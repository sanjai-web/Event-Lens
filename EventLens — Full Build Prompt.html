EventLens — Full Build Prompt

Use this as a spec to hand to a coding assistant (Claude Code, Cursor, etc.) or to work through yourself, feature by feature.

1. Project Summary

Build EventLens, an AI-powered event photo delivery platform for event photographers (weddings, corporate events, sports, schools) in India. Guests scan a QR code, take a selfie, and instantly get every photo they appear in via a face-matched gallery — delivered over web and WhatsApp. Photographers pay per event, not a yearly subscription.

Core differentiators to build in from day one:

  • Per-event pricing (not subscription)
  • WhatsApp-native delivery (not just a web app)
  • Offline-capable desktop uploader for bad-wifi venues
  • Auto-expiring data lifecycle (privacy + cost control)
  • Lean infra: single VPS, Cloudflare R2, Postgres+pgvector (no Redis, no managed vector DB)

3. Design System — Light Theme

Build a clean, warm, trustworthy visual identity — this is a product handling people's wedding/family memories, so avoid a cold "SaaS dashboard" feel.

Palette:

  • Background: #FAFAF8 (warm off-white, not pure white)
  • Surface/cards: #FFFFFF with soft shadow (0 2px 12px rgba(0,0,0,0.06))
  • Primary accent: #4F46E5 (indigo) or a warm coral #F97362 — pick one as the brand color, use sparingly
  • Text primary: #1A1A1A
  • Text secondary: #6B7280
  • Border: #E5E7EB
  • Success (LIVE/ACTIVE states): #22C55E
  • Warning (ARCHIVED): #F59E0B
  • Danger (DELETED): #EF4444

Typography:

  • Headings: a rounded/friendly sans (e.g. "Cal Sans", "Sora", or "Plus Jakarta Sans")
  • Body: "Inter" or "Manrope"
  • Generous line-height (1.6+) for readability on mobile — most guests will open galleries on phones

Components to design consistently:

  • Rounded corners (12–16px) throughout — cards, buttons, inputs
  • Soft shadows instead of hard borders for depth
  • Status pills for event lifecycle (Created/Live/Active/Archived/Deleted) using the color tokens above
  • Photo grid: masonry or square-crop grid with lazy-loaded thumbnails, subtle hover zoom
  • Empty states with friendly illustration/icon, not blank screens
  • Mobile-first for all guest-facing pages (gallery, selfie capture, payment) — desktop-first only for the photographer dashboard

Key screens to design:

  1. Landing/marketing page
  2. Photographer sign-up/login
  3. Photographer dashboard (event list with status pills, storage used, quick QR download)
  4. Create event flow (name, date, plan/size selection, Razorpay checkout)
  5. Event detail page (upload photos, view stats, guest count, gallery link, QR code, archive/renew controls)
  6. Public guest gallery (browse all photos, "Find my photos" selfie CTA)
  7. Selfie capture screen (camera permission, capture, processing state, matched results grid)
  8. Payment/checkout screen (if photo-selling enabled)
  9. WhatsApp opt-in confirmation screen

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE photographers (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  photographer_id UUID REFERENCES photographers(id),
  name TEXT NOT NULL,
  event_date DATE,
  status event_status DEFAULT 'created',
  plan_tier TEXT,
  storage_limit_mb INT,
  storage_used_mb INT DEFAULT 0,
  qr_code_url TEXT,
  face_search_enabled BOOLEAN DEFAULT true,
  archived_at TIMESTAMPTZ,
  deleted_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE photos (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  event_id UUID REFERENCES events(id) ON DELETE CASCADE,
  r2_key_original TEXT,
  r2_key_web TEXT,
  r2_key_thumb TEXT,
  width INT,
  height INT,
  face_processed BOOLEAN DEFAULT false,
  uploaded_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE guests (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  event_id UUID REFERENCES events(id) ON DELETE CASCADE,
  phone_number TEXT,
  whatsapp_opt_in BOOLEAN DEFAULT false,
  selfie_embedding vector(512),
  created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE face_embeddings (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  photo_id UUID REFERENCES photos(id) ON DELETE CASCADE,
  embedding vector(512),
  bbox JSONB,
  created_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX ON face_embeddings USING ivfflat (embedding vector_cosine_ops);

CREATE TABLE payments (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  event_id UUID REFERENCES events(id),
  razorpay_order_id TEXT,
  razorpay_payment_id TEXT,
  amount_paise INT,
  status TEXT,
  created_at TIMESTAMPTZ DEFAULT now()
);

6. Face Worker — Custom-Trained Model (built on the InsightFace framework)

Instead of calling InsightFace's pretrained buffalo_l/antelope models as a black box, train your own recognition model using InsightFace's open-source training code (github.com/deepinsight/insightface, recognition/arcface_torch), so the embedding model is yours end-to-end.

6.1 Why train your own, and the one thing to get right first

InsightFace's code (MIT licensed) is free for commercial use. Its pretrained models and the standard training datasets (MS1M, VGG2, CASIA-WebFace) are released for non-commercial research only. So before training anything:

  • Do not ship a model fine-tuned from their pretrained checkpoints, or trained on MS1M/VGG2/CASIA, in a paid product without separately checking licensing.
  • Build your training set from commercially-licensed or self-collected/consented face data (e.g. a licensed dataset like Glint360K's commercially-clear subsets where available, purchased datasets, or — more realistically for a v1 — a smaller curated/consented dataset plus heavy augmentation). Document this decision in your repo so it's auditable later.
  • Alternative if you want to de-risk this fast: start with the architecture and training code from InsightFace (ArcFace loss + IResNet backbone) but train from scratch or from a commercially-clean checkpoint, rather than their released weights.

6.2 Pipeline components (map to InsightFace repo structure)

Stage InsightFace component Your use
Face detection + alignment detection/scrfd (SCRFD) or RetinaFace Detect faces in uploaded event photos, output 5-point landmarks for alignment
Face recognition (embedding) recognition/arcface_torch Train your own ArcFace-loss embedding model
Backbone IResNet50 (accuracy) or MobileFaceNet (speed, CPU-friendly) Pick IResNet50 for server-side search accuracy; consider MobileFaceNet if you ever run on-device
Loss ArcFace / SubCenter-ArcFace / PartialFC ArcFace to start; PartialFC if your identity count grows very large (irrelevant at per-event scale, useful only if you later train one global model across users)
Export ONNX export scripts included in arcface_torch Export trained .pth → .onnx for fast CPU inference in the worker

6.3 Training prompt (use this as the actual build task)

Set up a face recognition training pipeline using the InsightFace arcface_torch codebase from github.com/deepinsight/insightface. Requirements:

  1. Clone recognition/arcface_torch, set up the PyTorch 1.6+ environment as specified in the repo.
  2. Build a training dataset in the MXNet .rec/.idx binary format (or their newer loader format) from [your chosen commercially-clean dataset / self-collected consented dataset]. Include a held-out validation split.
  3. Configure config.py with backbone r50 (IResNet50), loss arcface, margin 0.5, scale 64 — standard ArcFace hyperparameters — and point it at the new dataset.
  4. Train on GPU (rent a cloud GPU instance for the training run only — don't keep GPU always-on), monitor verification accuracy on your held-out set plus public benchmarks (LFW, AgeDB-30, CFP-FP) if licensing allows using them for eval only.
  5. Once validation accuracy plateaus, export the model to ONNX using the repo's export script.
  6. Wrap the ONNX model in an inference class using onnxruntime (CPU provider by default, CUDA provider when a GPU is available) that takes an aligned face crop and returns a 512-dim L2-normalized embedding.
  7. For detection/alignment, integrate SCRFD (also from the InsightFace repo) as a separate lightweight ONNX model — this does NOT need custom training, it's fine to use as-is since it's just bounding boxes/landmarks, not identity data.
  8. Benchmark end-to-end latency (detect + align + embed) per photo on the target VPS CPU; if too slow for batch processing during LIVE events, that's when you provision the spot GPU.

6.4 Worker service logic (unchanged regardless of model source)

  • Runs as a separate process/service, pulls jobs from pg-boss queue
  • On each job: download photo from R2 → run SCRFD detection + alignment → for each face, run your custom-trained ONNX embedding model → insert 512-dim vector into face_embeddings with bbox
  • On selfie search: embed the guest selfie the same way → SELECT photo_id FROM face_embeddings ORDER BY embedding <-> $1 LIMIT 100 filtered by cosine distance threshold (tune empirically against your own model's distribution — thresholds from InsightFace's published models won't transfer directly to a custom-trained model, so calibrate on your validation set)
  • Batch processing during LIVE events: spin up GPU (spot instance) only while an event is actively uploading; fall back to CPU (ONNX Runtime CPU provider) for low-volume/steady-state search
  • Version your model artifact (model_v1.onnx, model_v2.onnx) and store which version generated each embedding, since re-training later means old and new embeddings aren't comparable — you'll need a re-indexing migration path when you ship a new model version

7. WhatsApp Integration

  • Use WhatsApp Business Cloud API directly, or a BSP (Gupshup/Interakt) for faster approval
  • Phase 1 (build first): template message notification — "Your photos from [Event] are ready: [link]" sent when guest is matched and event photos are processed
  • Phase 2: inbound selfie via WhatsApp — guest sends a photo of themselves to the business number, webhook receives it, runs same selfie-search pipeline, replies with matched photo links or a gallery deep-link
  • Get WhatsApp template messages pre-approved (Meta requires this) before launch — start this early, approval can take days

8. Payments (Razorpay) — Per-Event Model

  • On event creation, calculate price based on plan_tier (storage tier chosen)
  • Create Razorpay Order, return order_id to frontend, open Razorpay Checkout
  • On success, Razorpay webhook fires → verify signature → set event status to live, set storage_limit_mb
  • Track storage usage on each photo upload; block further uploads and prompt upgrade if storage_used_mb exceeds limit
  • If enabling photo-selling to guests later: separate checkout flow per photo/album, use Razorpay Route to split proceeds if multiple photographers on one event

9. Event Lifecycle Automation

Scheduled job (pg-boss cron or a simple daily cron):

  1. live → active: triggered manually by photographer ("End Event") or automatically N days after event_date
  2. active → archived: after configurable retention window (default 30 days) — delete r2_key_original and r2_key_web, keep r2_key_thumb only
  3. archived → deleted: after further window (default 60 days total) — delete all R2 objects, delete rows from face_embeddings and guests.selfie_embedding
  4. renew: photographer can pay again to reset the archive timer and restore full-res access before deletion happens

Surface all of this clearly in the dashboard with countdown timers so photographers aren't surprised by auto-deletion.

10. Non-Functional Requirements

  • Security: rate-limit /selfie-search aggressively (per-IP + per-event); presigned URLs short-lived (15 min); JWT auth with refresh tokens; validate file types/sizes on upload
  • Privacy: explicit opt-in checkbox before selfie capture, clear copy on what happens to face data and when it's deleted; "browse without selfie" always available as an alternative
  • Performance: thumbnails served from Cloudflare cache; lazy-load gallery grids; presigned direct-to-R2 uploads (never proxy image bytes through the API server)
  • Compliance: DPDP Act-aware consent language; publish a simple privacy page explaining biometric data handling and deletion timelines
